# End-to-end application validation

Date: 2026-09-14

## Scope and baseline

This record covers the read-only application, browser, health, schema and clean-checkout checks assigned under [the end-to-end specification](../../docs/superpowers/specs/2026-09-14-end-to-end-validation-design.md) and [plan](../../docs/superpowers/plans/2026-09-14-end-to-end-validation.md). The controlled n8n executions and guarded relational test fixture are reported separately. The tested committed baseline was `eaa588b`; the working branch is `test/end-to-end-validation`. The application host used an existing external ignored `.env` only through `/tmp/sonrisa-correction-tools/run.py`, which verifies `current_database() = sonrisa_dev` before launching. No connection value was printed or copied into this evidence.

Before runtime fixtures were created, a read-only SQL projection returned four users, five alerts, one enabled alert, three owners with Slack and three with Email, and one alert for the default configured management owner. This matched the [completed admin milestone evidence](2026-09-14-operational-admin-validation.md). A later read-only schema query observed only `users`, `alerts` and `__EFMigrationsHistory` product tables: the users table has identifier, revision and nullable Email/Slack destination columns; alerts has owner, name, enabled state, revision and typed earthquake condition columns. Four product indexes exist: two primary keys and `ix_alerts_owner_id`/`ix_alerts_enabled_event_type`. Six EF migrations were applied. A count of seven users/nine alerts during the later schema query was transient: the controller had begun generated runtime fixtures, so it is not a changed baseline or cleanup result. `dotnet ef migrations has-pending-model-changes --project src/Sonrisa.Web --no-build` reported no model changes.

## Live application and browser

An owned Production-mode host on `127.0.0.1:5298` used the verified external DEV connection. `/health/live` and `/health/ready` returned HTTP 200 with body `Healthy`; `/admin` and `/alerts` returned 200. The owned host was stopped, then restarted on the same port with an unavailable OTLP HTTP endpoint at `127.0.0.1:1` and a 100 ms exporter timeout. Liveness, readiness, `/admin`, `/alerts` and `/settings/notifications` remained HTTP 200. Both owned positive hosts were stopped. The no-endpoint and unavailable-endpoint hosts exercised live request/startup independence; they do not prove an external telemetry backend accepted signals.

The installed local Playwright package and cached Chromium headless shell were used without adding a repository dependency. The package's default browser revision was absent, so launch specified the already cached executable. Before runtime fixtures, browser navigation returned HTTP 200 for `/admin`, `/admin/users`, `/admin/alerts`, `/alerts` and `/settings/notifications`. The six summary values matched the read-only SQL baseline (4/5/1/4/3/3); the users, alerts and normal management tables had 4/5/1 rows. No admin form, browser page error or non-loopback browser request was observed.

After the controller removed its exact generated fixtures and confirmed the original row digests, the owned host was started once more for a private row-level browser comparison. Fresh read-only SQL projections supplied expected owner counts/channel indicators and alert owner/name/type/state/condition/channels without printing destination values. Chromium matched every overview metric, all four owner rows, all five alert rows, and the one-alert current-owner management boundary. None of the persisted destination values appeared in any admin page HTML; all three admin pages had zero forms. `/settings/notifications` returned 200, with zero browser page errors or external requests. The host was stopped afterward. No new screenshot or responsive inspection was made; the previous [admin evidence](2026-09-14-operational-admin-validation.md) contains desktop/mobile captures and inspection.

## Controlled database and telemetry failure cases

Separate owned Production-mode hosts at `127.0.0.1:5299` used, in turn, absent database configuration, a syntactically malformed value, a parseable value with a blank Host, and a synthetic refused connection to loopback port 1. No case reached shared DEV. Each returned `/health/live` HTTP 200 `Healthy` and `/health/ready` HTTP 503 `Unhealthy`. After the correction below, each returned HTTP 503 for `/admin`, `/alerts` and `/settings/notifications`. Every owned negative host was stopped. Private scans of their captured logs found no full supplied connection input or synthetic password sentinel; raw logs were not retained.

The first refused-host run exposed a real prior-milestone failure: admin returned 503 but `/alerts` and `/settings/notifications` returned 500. A red HTTP test showed `NpgsqlExecutionStrategy` wrapping the connection-refused `NpgsqlException` in `InvalidOperationException`, which the two management services did not classify as a database failure. The adjacent parseable blank-Host case raised an uncaught `ArgumentNullException` during Npgsql connection setup, because those services accepted syntactically parsed strings without validating Host. Their error handling was narrowed to mirror the already reviewed admin page behavior: require a nonblank parsed Host and catch only a wrapped database/timeout exception, while retaining existing direct database/timeout handling. No response contains the provider exception or connection text.

The two new HTTP regression theories each cover `/alerts` and `/settings/notifications` with a refused loopback connection and a parseable blank-Host connection. Refused cases failed 2/2 before correction with the EF wrapper; blank-Host cases failed 2/2 before correction with `ArgumentNullException`. After correction, `dotnet test tests/Sonrisa.Web.Tests/Sonrisa.Web.Tests.csproj --no-restore --filter 'FullyQualifiedName~Refused_database_returns_generic_unavailable_page|FullyQualifiedName~Parsed_connection_without_host_returns_generic_unavailable_page|FullyQualifiedName~AlertPagesTests|FullyQualifiedName~AlertManagementServiceTests' --logger 'console;verbosity=minimal'` passed 14/14 with zero skips. The four-case real-host matrix then passed all health and management assertions. `dotnet build Sonrisa.sln --no-restore` passed with zero warnings/errors, and `git diff --check` passed. The controller will run broader suites after task review.

`dotnet test tests/Sonrisa.Web.Tests/Sonrisa.Web.Tests.csproj --no-restore --filter 'FullyQualifiedName~ObservabilityTests' --logger 'console;verbosity=minimal'` passed 11/11 with zero skips. Those [ObservabilityTests](../../tests/Sonrisa.Web.Tests/ObservabilityTests.cs) cover request trace/log correlation, safe redaction, common/signal OTLP endpoint routing and invalid configuration. The live hosts here did not capture or inspect exported OTLP payloads. Npgsql spans remain deliberately absent under [ADR-009](../../docs/adr/ADR-009-use-opentelemetry-logs-and-request-traces.md).

## Clean-checkout reproducibility

`git archive HEAD` created a disposable tracked-file snapshot of `eaa588b` under `/tmp/sonrisa-e2e-clean-eaa588b`; it contained no `.env` and ran no application or services. From that snapshot, in README order: `dotnet tool restore` restored `dotnet-ef` 10.0.12; `npm ci` added 33 packages, audited 34 and reported zero vulnerabilities; `npm run css:build` completed with Tailwind 4.3.3 and generated an 11,195-byte CSS file; `dotnet build Sonrisa.sln` restored both projects and succeeded with zero warnings/errors. npm also warned that one `@parcel/watcher@2.5.1` install script is not covered by the current `allowScripts` setting; CSS still built. The disposable snapshot was removed afterward. This proves the committed baseline's reproducible tool/CSS/build path, not the uncommitted correction or database/runtime behavior.

## Boundaries

The application remains an unauthenticated MVP surface; the admin area is not a production security boundary. Successful readiness proves DEV PostgreSQL connectivity at the time of the check, not privilege isolation, schema correctness or n8n readiness. The existing accepted DEV credential/TLS exception remains under [ADR-007](../../docs/adr/ADR-007-accept-current-dev-database-access.md). This application task performed no shared database writes, migrations, n8n operations or transport sends.
