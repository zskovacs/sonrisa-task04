# Runtime simplification design

Approved by the user on 2026-09-14 after the read-only [inspection](../../../evidence/reviews/2026-09-14-runtime-simplification-inspection.md) of the committed code, applied DEV schema, hosted n8n 2.38.7, and three inactive workflows. This is a deliberate correction to the completed [first runtime milestone](../../../evidence/reviews/2026-09-14-first-runtime-validation.md) and [SMTP extension](../../../evidence/reviews/2026-09-14-smtp-delivery-validation.md), not a rewrite of their history. The [request](../../../prompts/025-simplify-n8n-runtime-architecture.md) and subsequent approval authorize the bounded change below.

## Boundary and migration

PostgreSQL contains product configuration only: `public.users` and `public.alerts`, plus EF migration history. Keep the existing ownership-aware management UI, one inline `earthquake`/`magnitude`/`gte`/`number` condition per alert, and shared `email_destination` and `slack_destination` columns on users. There is no `AlertChannel` table in the current model; do not add one. The application remains configuration-only. EF Core owns schema changes; n8n reads product configuration directly.

Remove `public.notification_deliveries` and then `public.source_events` through a reviewed **forward EF migration**. These tables and their retained DEV rows have been committed and applied; dropping them permanently removes those records. Recheck row counts and the exact `sonrisa_dev` target immediately before application, inspect the generated migration and SQL, and apply only after the new workflow's local and mocked validation is ready. An optional, restricted backup may be kept outside Git; no backup, row dump, credential, or connection string belongs in tracked files. Preserve every historical migration and designer unchanged. The final EF model/snapshot contains only configuration entities. The migration `Down` can recreate empty runtime tables but cannot recover deleted rows; document that limit.

## One manually operated DEV runtime

Create one inactive manual workflow named `Sonrisa - Process Alerts - DEV`. Its operator fields default to `mode=live` and an empty fixture, with no schedule, webhook, queue, delivery-ID selector, or automatic background drain. A full manual live run can send more than one notification when multiple fetched events match. Its readable canvas is one path:

```text
Manual input → live USGS all-hour fetch or explicit synthetic fixture
→ same bounded canonical normalization
→ Remove Duplicates (within input)
→ Remove Duplicates (seen in previous executions)
→ load all enabled alerts joined to their owners' shared destinations
→ evaluate one typed magnitude threshold and expand configured channels
→ Loop Over Items, batch size 1
→ Switch(channel): Slack | email unsupported | other unsupported
→ transport/result or safe diagnostic → return to loop
```

The live USGS and explicit fixture paths use the same normalizer. A fixture is marked `demo.usgs` and cannot be selected by a future live trigger. Keep only the small canonical event fields already needed for matching and messages: `contract_version: 1`, `source`, `external_id`, `event_type`, `occurred_at`, `title`, optional `source_url`, and typed magnitude data. No event is persisted in the product database. Future sources may add a fetch/normalization branch feeding this common path; this milestone adds no new source.

Two native Remove Duplicates nodes are required on n8n 2.38.7: first compare `source` and `external_id` within this input; second use `removeItemsSeenInPreviousExecutions` / `removeItemsWithAlreadySeenKeyValues` with the key expression `source + ':' + external_id`, node scope and history size `10000`. Retain the replacement workflow and node identities after validation. The installed implementation checks existing count plus input count against the history size **before filtering** and throws when the bound is exceeded. It does not roll history forward. This is limited, n8n-owned technical state, not an atomic claim across concurrent executions or a guarantee after history loss/recreated identity. No Sonrisa table, queue, or workaround is added. Provider ID changes can cause the same physical earthquake to be processed again; alias reconciliation remains deferred. An event marked seen before delivery can be lost after downstream failure and will not be retried by the next poll. Alerts created or edited after an event was seen do not rematch that historical event.

The configuration query selects enabled alerts across **all** owners through `alerts.owner_id = users.id`; it must not depend on the management application's configured current owner. Evaluation accepts only the existing typed condition and a finite numeric magnitude and threshold. Unsupported/malformed configuration, disabled alerts, and malformed events never produce a false match. A match expands the owner's configured non-secret Slack and email destinations into separate channel items. Validate destination syntax conservatively before any send; diagnostic output contains codes and safe identifiers, never credential values or raw destination payloads. Unsupported channels are visibly skipped without claiming delivery. No per-alert or per-channel database writes occur.

The Loop Over Items node uses batch size 1 so each notification reaches its branch independently. The Slack node uses the existing `Sonrisa DEV Slack` credential and a bounded, escaped plain-text message, with mentions/unfurls disabled as in the validated earlier implementation. Set `retryOnFail: true`, `maxTries: 5`, `waitBetweenTries: 5000`, and `onError: continueErrorOutput` on Slack. Five means **five total attempts**. The exhausted error output goes to a safe diagnostic and returns to the loop, as does success. A failed notification A must not prevent later notification B from being attempted. No custom retry loop, error-state table, circuit, or recovery process is added. n8n execution history carries diagnostics. A transport ambiguity can yield duplicate or lost external messages; delivery is best-effort and no exactly-once claim is made.

The Switch includes an explicit email branch for the current shared email destination but this milestone **does not send email**. It reports `email_transport_not_implemented` and returns to the loop. Implementing email in the **same workflow branch** is the required next runtime milestone, not optional future polish. The prior SMTP branch and its controlled validation remain historical evidence; the remote three-workflow architecture is being replaced, not represented as never having existed. Other unsupported channel types also return safely with a diagnostic.
